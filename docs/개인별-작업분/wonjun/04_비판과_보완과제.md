# IA · UJ · PRD 비판과 보완 과제

> 이 문서는 정리 전 문서를 대상으로 한 비판이다. 반영 현황은 맨 아래 "반영 현황"에 있다.

범위: `00_한눈에보기.md`, `01_IA.md`, `02_UJ.md`, `03a_PRD_보충.md`. 각 지적은 문서 원문, 실제 DB 정책(`pg_policies` 조회), 코드·시험 현황과 대조해 **확인됨 / 부분 확인 / 오독(기각)**으로 구분했다.

## 총평
PRD는 "권한을 서버/DB에서 강제한다"고 쓰지만, 현재 DB 정책은 담당자가 자기 요청의 상태를 직접 `approved`·`done`으로 바꾸는 것을 막지 못한다. 그 위에 마감까지 약 3일 남은 3명 팀에 맞지 않는 크기의 필수 범위(Must 20개)와 과한 상태 모델을 올려 두었다.

## 확인된 결함

### 1. DB 접근 규칙이 문서의 핵심 보안 주장과 충돌 — 상 (확인됨)
- 문서: AC-02 "행동별 권한을 서버에서 강제. … 자기 요청 승인·자기 완료 검토·회원의 역할 승격 거부", FR-16 "원본 삭제 불가".
- 실제(DB 조회): `patch_requests`의 `requests_own`은 `FOR ALL`, 조건 `requester_id = auth.uid()`. 담당자는 로그인 키만으로 자기 요청의 **모든 열을 수정·삭제**할 수 있다. 상태 규칙은 앱 코드(`requestStatus.ts`)에만 있고 DB에는 상태 목록 제약뿐이다.
- 같은 문제: `matches_decide`는 담당자에게 자기 자산 후보의 모든 열(점수·판정자 포함) 수정을 허용한다. `requests_admin_decide`는 관리자가 모든 열을 바꿀 수 있게 둔다(승인 외 필드 변조 가능).
- 시험에서의 위험: 담당자 계정으로 상태를 직접 `done`으로 바꾸는 요청이 통과하면 "서버에서 강제"는 거짓이 된다.
- 보완(초안, 미적용): 담당자 정책을 읽기와 `status='submitted'` 신청 INSERT로만 줄이고, 모든 상태 전이는 서버 경로 또는 보안 함수 한 곳에서 규칙·이력과 함께 처리한다. `matches`는 열 단위 권한으로 확인 관련 열만 허용한다. 이 취약점을 PRD 8절의 "현재 구현과의 차이"에 명시하고, "담당자가 상태를 직접 바꾸면 거부"를 실제 시험 5개 중 하나로 둔다.

### 2. "독립 관리자"와 관리자 1명 환경의 모순 — 상 (확인됨)
- FR-14 "독립 관리자 수락 시에만 done"과 권한표 "요청자/처리자와 다른 admin. 같은 admin의 사전 승인과 사후 검토는 허용"이 한 문서에 공존한다. 관리자가 1명이면 "독립"은 요청자와 다르다는 뜻일 뿐이다.
- 첫 범위에서 관리자는 요청을 만들 수 없으므로 "자기 승인 금지"는 실제로 시험할 상황이 없다.
- 보완: AC에서 "독립"을 지우고 "관리자 ≠ 요청자, 승인과 근거 수락은 별도 행위"로 쓴다. 시연에 관리자 2명을 두면 분리를 보일 수 있다.

### 3. 범위·공수가 남은 시간에 비해 과다 — 상 (확인됨)
- 필수(Must)가 FR 20개(FR-01·02·03·05·06·07·08·11·12·13·14·15·16·18·19·20·21·40·41·42)이고 공수는 88~148시간(예비 포함)이다. 3명이 3일에 나누면 1인당 하루 약 10~16시간이다. 문서는 "범위를 팀이 재합의"하라고만 쓰고 결정하지 않았다.
- 가상 자산 한 건의 정상 흐름(CUJ-1~5)에는 FR-40(실패 복구)·41(취소 경합)·42(완료 무효)가 필요하지 않은데 Must다.
- 공수표에 발표 준비, 제출 문서, 시연 데이터가 없다.
- 보완: Must를 약 14개(FR-01·02·03·05·06·07·08·11·12·13·14·16·18·19)로 줄이고 FR-15·40·41·42는 Should로 내린다. 보류는 사유 기록 한 가지로 시작한다. "10/27까지 시연할 최소 흐름"을 먼저 못 박는다.

### 4. 상태 모델 과설계와 빠져나갈 수 없는 상태 — 상 (부분 확인)
- 착수한 뒤 작업 실패 없이 일시중지한 요청을 포기하려면: 취소 불가(착수 이력), 반려 불가(복구 검토 우회 금지), `failed`는 "작업 실패 사건"이 전제다. 남는 길은 무기한 보류나 실패 기록으로 우회하는 것뿐이다(실패·복구 경로에서 "미적용/무영향 검증 후 failed"로 닫을 수는 있으나 의미를 비튼다). 보류 건이 활성 요청 중복 방지를 계속 점유한다.
- 미착수 취소가 "철회 요청 → 관리자 미착수 확인 → 확정" 3단계라 관리자 1명 환경에서는 모두 관리자 대기다.
- 상태가 6개에서 9개(+보조 상태)로 늘고, 보류 하나에 사유 5가지 이상이 얽혀 있다.
- 보완: 신청자가 승인 전 요청은 직접 취소, 착수 후 포기는 `failed`(사유=포기)로 닫게 한다. 보류는 사유 필드 하나로 시작한다.

### 5. 자산 보완 경로의 공백 — 중 (확인됨)
- UJ CUJ-1은 버전 미상일 때 "자산 보완으로 이동"하라고 하지만, 첫 범위는 자산 식별 정보 수정을 제한한다(FR-04). 버전 미상 자산은 계속 미확인이고 미확인은 신청이 막히므로(AP-04) 요청 흐름에 들어갈 수 없다. Ex-09(요청 중 자산 정보 변경)는 수정이 없어 발생할 수 없는 시나리오다.
- 보완: 식별 정보 수정을 요청 생성 전에만 허용(이력은 한 줄 기록)하거나, 미상 버전을 입력 단계에서 막고 Ex-09를 뺀다.

### 6. 인수 기준(AC)의 시험 가능성 — 중 (부분 확인)
- 표는 AC와 QA를 1:1로 연결한다고 하지만 AC 하나에 여러 시험이 들어 있다(예: AC-42는 오류 판정·정정·무효·후속 연결·원본 보존·중복 차단). "~금지" 형태는 입력과 기대 결과로 쓰여 있지 않다. AC-40·41은 동시성 시험을 요구한다.
- Should/Could(FR-09·22~26)에도 AC를 모두 써서 분량이 늘었다.
- 보완: 필수 FR마다 "입력 → 기대 결과" 한 쌍으로 다시 쓰고, Should/Could는 한 줄 목록으로 둔다.

### 7. 문제 정의 근거와 측정 계획의 무게 — 중 (의견, 일부 타당)
- 문제 정의가 "~할 수 있다"로 시작하고 발생 빈도·손실이 미측정인데, 완료 근거 기준(EQ 5개)·적용 확인 절차(AP 5단)·측정 실험 설계(순서 교대·중앙값)까지 있다. 3명 과제에서 실행하기 어려운 측정 약속이다.
- 보완: 측정은 "시연에서 근거 연결 100%, 권한 위반 거부 N건"처럼 시험 기준 하나로 줄인다.

### 8. 정본 불명과 구현 상태 표기 — 중 (확인됨)
- 저장소의 `docs/PRD.md`와 이 폴더의 `03a_PRD_보충.md`가 따로 있어 어느 쪽이 정본인지 정해지지 않았다.
- "요구사항 29개 모두 구현 확인대기·QA No Run"은 화면·저장·QA 기준으로는 맞지만, 요청 상태 전이·체크리스트·점수·매칭·KEV 변환 등 **도메인 규칙의 단위 시험 50건이 이미 통과**한다는 사실을 가린다. 열 이름을 "시험 있음/없음"으로 나누는 편이 정확하다.
- 새 상태·열(작업 키·버전 등)과 현재 `0001_init.sql`의 차이를 정리한 표가 없다.

## 발표·시험에서 질문받으면 막힐 곳
1. 담당자 계정으로 요청 상태를 `done`으로 직접 바꾸면 통과하지 않는가? (보완 1 전에는 통과한다.)
2. 관리자가 1명인데 "독립 검토"를 어떻게 보여 주는가? 로그인은 아직 가짜 사용자(`fake-member`·`fake-admin`)이고 최초 관리자도 정해지지 않았다.
3. 저장소가 공개 상태인데 제출은 비공개를 요구한다. 제출 일시도 공식 확인 전이다.
4. 담당자가 허위 결과를 입력하면 어떻게 아는가? (완료 근거는 사람이 입력한 기록이며 장비 검증이 아니라고 문서가 밝히고 있다. 근거 파일·교차 확인 같은 보완책은 없다.)
5. 폐쇄망 공장에서는 Google 로그인과 KEV 동기화가 어떻게 가능한가? (Google 로그인은 과제 필수 조건이라 교체할 수 없다. 한계로 문서에 적는 것이 맞다.)

## 검증 후 기각한 지적
- "FR-10(후속 대시보드)과 IA가 모순": FR-10은 "첫 범위는 요청 목록 필터로 대체"라고 명시했다.
- "`/admin`과 `/admin/requests`가 중복": `/admin`은 첫 버전에서 승인 목록으로 안내만 한다.
- "FR-19가 자산 편집 이력까지 요구": FR-19의 대상은 회원 입력·요청·근거·상태/정정 이력이며 자산 편집 전후 이력은 FR-04(후속)다.
- "AS-03-P가 후속 화면": 첫 버전은 식별 정보·관련 요청, 후속은 변경 이력이다.
- "Google 로그인을 사내 계정으로 교체": 과제 필수 조건이라 채택하지 않는다.
- "신청자=처리자를 분리 가능하게": 첫 버전의 의도적 단순화이며 근거는 약하다. 분리 지정은 후속 과제로 남긴다(기각이 아니라 보류).

## 보완 우선순위
1. 담당자의 상태 직접 변경 차단(DB 정책 수정, 시험 추가)
2. Must를 약 14개로 줄이고 최소 시연 흐름 확정
3. "독립" 표현 정리와 관리자 2명 시연 계정 준비
4. 자산 수정 허용 범위 결정(요청 전에만)
5. AC를 "입력 → 기대 결과"로 다시 쓰기
6. 정본 지정·구현 상태 열을 "시험 있음/없음"으로 바꾸기
