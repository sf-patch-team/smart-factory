# Mom Test 인터뷰 기록 (페르소나)

> 작성 2026-10-22 · 연결: `docs/00-리서치-주제결정.md` · 이후 PRD의 FR, UJ의 CUJ와 ID로 연결한다.

## ⚠️ 이 기록의 성격 (반드시 읽기)
- 아래 인터뷰는 **AI가 페르소나를 연기해 만든 가상 인터뷰**다. 실제 사람의 말이 아니므로 **증거가 아니라 가설**이다.
- 답변은 조사한 자료(`00` 문서의 출처)와 일반적 업무 상식에서 끌어냈다. 각 인사이트에 **근거 구분**을 달았다.
  - `조사` = 앞서 찾은 자료에 근거 · `추정` = 그럴듯하지만 근거 없음 → **실제 인터뷰에서 검증해야 함**
- 발표·PRD에서 "사용자 인터뷰 결과"라고 쓰지 않는다. "가상 페르소나 인터뷰로 세운 가설, 실제 [N]명 확인"으로 쓴다. (실제 확인 칸은 아래 5번에서 채운다.)

## 1. Mom Test 규칙 (질문 만들 때 지킨 것)
1. 우리 아이디어를 말하지 않는다(말하면 상대가 좋은 말만 한다).
2. **미래·의견이 아니라 과거의 실제 행동**을 묻는다. "~하면 쓰시겠어요?" 금지, "마지막으로 ~했을 때 어땠나요?"
3. 칭찬·"좋네요"는 데이터가 아니다. **구체적 사실, 쓴 시간·돈·도구, 겪은 고통**만 기록한다.
4. 약속(시간·소개·돈)이 나오면 진짜 신호, 말뿐이면 약한 신호.

## 2. 공통 질문지 (모든 인터뷰에서 쓴다, 제품 설명 없음)
| # | 질문 | 알아내려는 것 |
|---|---|---|
| Q1 | 가장 최근에 **보안 취약점 때문에 장비·시스템을 패치하거나 점검한 일**을 처음부터 끝까지 말씀해 주세요. | 실제 흐름, 담당자, 단계 |
| Q2 | 그 취약점은 **어떻게 알게 되셨나요?** 우리 장비에 해당하는지는 어떻게 확인하셨나요? | 인지 경로, 매칭을 사람이 하는 비용 |
| Q3 | 그 과정에서 **가장 번거롭거나 시간이 오래 걸린 부분**은? 마지막으로 그런 게 언제였나요? | 진짜 고통과 빈도 |
| Q4 | 지금은 **무엇으로 기록·관리**하세요?(엑셀, 메일, 메신저, 도구) 마지막으로 그걸 고친 적은? | 현재 대안, 전환 비용 |
| Q5 | 이 문제를 줄이려고 **직접 해본 것**(도구 도입, 규칙 만들기)이 있나요? 안 된 이유는? | 이미 시도한 것, 막힌 이유 |
| Q6 | 누가 **승인**하고 누구에게 **보고**하나요? 마지막으로 승인이 늦어졌던 건? | 요청 흐름·권한 |
| Q7 | 이 얘기를 더 잘 아는 **다른 분**을 소개해 주실 수 있나요? | 약속 신호 |

## 3. 페르소나별 인터뷰 (가상)

### P1. 설비·제어 엔지니어 (OT) — 이름: 가상 "김제어", 공장 제어팀 8년차
- Q1: 지난 분기 엔지니어링 PC(Windows)가 취약 판정을 받았는데, 가동 중인 라인과 연결돼 있어 **정기 점검 주간까지 못 건드렸다**. 장비 벤더에 "패치해도 되는지" 확인 메일을 먼저 보냈다.
- Q2: 보안팀이 보낸 목록을 받는다. 우리 설비에 해당하는지는 **엑셀 자산 목록과 눈으로 대조**한다.
- Q3: 가장 힘든 건 패치 자체보다 **언제 적용할 수 있는지(점검 창)와 벤더 승인 대기**다. 급해도 라인을 세울 수 없다.
- Q4: 엑셀 자산 목록, 마지막 갱신은 몇 달 전이다. 현장에서 장비를 바꾸면 반영이 늦다.
- Q6: 승인은 공장장·보안팀 둘 다 필요하고, 한쪽이 늦으면 전체가 멈춘다.
- **추출한 사실**: 패치는 **"할 수 없음/나중에"**가 정상 상태. 점검 창과 벤더 확인이 병목. 자산 목록이 낡았다. (근거: `조사`—노후 설비·수기 기록 / 나머지 `추정`)

### P2. IT 인프라 운영자 — 가상 "이서버", 사내 서버·네트워크 5년차
- Q1: 방화벽 장비 취약점 공지가 떠서 당일에 해당 모델·펌웨어를 확인하고 야간에 패치했다.
- Q2: 벤더 메일, 보안 뉴스, 보안팀 전달 등 **경로가 여러 개**다. 하루 수십 건 중 우리 것은 몇 건뿐이다.
- Q3: **"우리 것인지" 가려내는 시간**이 가장 크다. 같은 공지를 여러 채널로 받아 중복 확인한다.
- Q5: 알림 도구를 써봤지만 **알람이 너무 많아 결국 무시**하게 됐다.
- **추출한 사실**: 가치는 "해당 여부 자동 판별 + 알람 줄이기". (근거: `조사`—알람 피로 / 나머지 `추정`)

### P3. 정보보안 담당 — 가상 "박보안", 보안팀 7년차
- Q1: KEV는 이미 우선순위 참고로 본다. 문제는 **자산 목록이 부정확해 해당 여부를 확신 못 하는 것**이다.
- Q3: 감사 때 **"언제 누가 승인하고 누가 조치했는지 증적"**을 모으는 데 며칠이 걸린다. 메일·메신저에 흩어져 있다.
- Q4: 티켓 도구와 엑셀을 섞어 쓴다.
- Q6: 예외(패치 못 하는 경우)는 **사유와 기한을 적어 승인**받아야 한다.
- **추출한 사실**: 이력·증적이 핵심, **예외(유예) 승인** 흐름이 필요. 자산 정확성이 전제. (`추정`)

### P4. 공장장 / 생산 관리자 — 가상 "최공장", 현장 총괄
- Q1: 보안팀 요청이 오면 **"라인이 얼마나 서야 하는지"**부터 묻는다.
- Q3: 위험이 얼마나 큰지 **숫자나 한 줄 설명이 없으면 결재하기 어렵다.** 막연한 "취약합니다"는 미룬다.
- Q6: 하루 이틀 가동 중단은 큰 손실이라 근거가 분명해야 승인한다.
- **추출한 사실**: 결재자에게는 **"왜 지금 해야 하는지"를 근거와 함께 한 화면**으로 보여 줘야 한다. 영향 범위(라인·설비) 정보가 필요하다. (`추정`)

### P5. 외부 유지보수 협력사 — 가상 "정협력", 장비 납품·유지보수 업체
- Q1: 고객사 장비 패치는 **원격접속 허가 + 작업 일정 합의** 후에 한다.
- Q3: 고객사마다 **요청 방식이 달라**(메일·전화·메신저) 이력이 안 남는다.
- **추출한 사실**: 외부 작업자 역할은 후속 확장 후보(이번엔 범위 밖). (`추정`)

### P6. 신입 IT운영자 — 가상 "한신입", 입사 1년차
- Q1: 선배가 "이거 급하다"고 하면 따라 한다. **기준은 잘 모른다.**
- Q3: 위험 목록이 길면 어디서부터 해야 할지 모르겠고, **왜 급한지 설명이 없으면** 판단을 못 한다.
- Q5: 정리된 기준표가 있으면 좋겠다고 했지만 직접 만들 시간은 없다.
- **추출한 사실**: 우선순위에 **근거(점수 구성)**를 같이 보여 줘야 한다. (`조사`—우선순위를 못 정함 / `추정`)

## 4. 종합: 요구와 반영 (가설)
| # | 발견(가설) | 근거 구분 | 설계에 미치는 영향 | 연결 |
|---|---|---|---|---|
| H1 | 패치는 "지금 못 함"이 정상이다(점검 창·벤더 확인) | 추정 | 요청 상태에 **보류(유예)** 와 **적용 예정일** 추가 | 요청 흐름 |
| H2 | "우리 것인지" 가리는 시간이 가장 큰 비용이다 | 추정 | 매칭 + 사람 확인 단계가 핵심 가치 | 매칭 |
| H3 | 자산 목록이 낡고 부정확하다 | 조사+추정 | 자산 **마지막 확인일**, 담당자, 변경 이력 필드 | 자산 |
| H4 | 감사용 증적(누가·언제·무엇을)이 필요하다 | 추정 | **모든 상태 변경 이력 + 사유** 기록 → 관리자 열람 | 이력, KPI |
| H5 | 결재자는 근거 한 줄과 영향 범위가 필요하다 | 추정 | 요청 화면에 **"왜 지금(점수 구성)"과 영향 설비** 표시 | 우선순위 |
| H6 | 알람이 많으면 무시한다 | 조사 | 상위 N건만 기본 표시, 나머지는 접기 | 목록 |
| H7 | 예외(유예) 승인 사유·기한이 필요하다 | 추정 | 유예 요청 시 **사유 + 재검토일** 필수 | 요청 흐름 |
| H8 | 외부 협력사 역할이 있다 | 추정 | **이번 범위 밖**, 확장 후보로 ADR/PRD에 기록 | 범위 |
