## 1. 한 장 요약

- **무엇을:** 공장 자산의 취약점 조치를 요청 → 승인 → 처리·근거 제출 → 관리자 검토까지 한 요청에 묶어 기록하는 웹앱.
- **누가:** 요청하고 처리하는 담당자(member), 승인하고 근거를 검토하는 관리자(admin).
- **아닌 것:** 패치를 대신 실행하는 도구가 아니다. 장비에 접속하지 않고, 호환성을 자동 판정하지 않는다.
- **문제(가설):** 완료 회신이 와도 어느 자산에 무엇을 적용했는지, 어떻게 확인했는지가 요청과 이어지지 않아 기록을 다시 맞춰 봐야 할 수 있다. 얼마나 자주 생기는지, 손실이 얼마인지는 재 본 적이 없다. **확인 필요.**
- **현재 상태:** 앱과 DB 기준 시험은 아직 한 번도 돌리지 않았다. 도메인 규칙과 가짜 저장소 단위 시험 50건만 통과했다.

## 2. 사용자

| 역할 | 하는 일 | 지금의 불편 → 우리가 주는 것 |
|---|---|---|
| member | 자산 등록, 요청 작성, 처리, 근거 제출 | 요청·대장·메일을 따로 대조 → 요청 하나에서 다음 행동과 근거 확인 |
| admin | 승인·반려, 근거 수락, 전체 조회 | 부서별 회신 취합 → 전체 목록·결과·보류 사유·이력 조회 |

- 첫 버전은 신청자와 처리자를 같은 member로 보고, 승인·검토는 반드시 다른 admin이 한다.
- 새 "검증자" 역할은 만들지 않는다. 역할 관리 화면, 협력사 계정, 다단 승인은 범위 밖이다.
- 이 사용자 설명은 팀의 가정이다. 실제 현장 담당자에게 확인한 것이 아니다. **확인 필요.**

## 4. 첫 버전 필수 요구 15개

입력 → 기대 결과로 적는다. QA 번호는 `QA-FR-번호`.

| FR | 요구 | 입력 → 기대 결과 |
|---|---|---|
| 01 | Google 로그인 | 첫 로그인 → member 생성. 재로그인 → 같은 계정. 취소·실패 → 비로그인 |
| 02 | 권한 분리 | 남의 자산 조회, 자기 요청 상태 직접 변경, 자기 역할 변경, 자기 요청 승인 → 모두 서버·DB가 거부 |
| 03 | 자산 입력 | 이름·벤더·제품·버전(모르면 미상)·담당자 → 저장 후 같은 값 조회. 필수 누락 → 거부 |
| 05 | KEV 갱신 | 관리자가 갱신 → 저장 후 개수 일치. 외부 실패 → 이전 정상본 유지·실패 표시 |
| 06 | 수신 상태 표시 | 정상 → 값과 받은 시각. 0건 → "내용 없음". 실패 → "못 읽음"과 마지막 성공 시각 |
| 07 | 후보 제시 | 벤더·제품이 비슷한 자산–KEV 쌍 → 후보로 저장. 후보만으로 "취약 확정" 표시 안 함 |
| 08 | 적용 여부 확인 | 담당자가 해당/해당 없음 선택 → 판단자·시각·공식 자료 저장. 근거 부족 → 미확인 유지 |
| 11 | 요청 작성 | 적용 확인·시험 기준·복구 계획 입력 → 신청 당시 자산 정보와 함께 저장. 같은 자산·위험의 활성 요청 있으면 거부 |
| 12 | 내 요청 조회 | 상태와 다음 행동 표시. 없음과 조회 실패를 구분 |
| 13 | 승인·반려 | 다른 사용자인 admin 승인 → approved. 반려는 사유 필수. 재신청은 새 ID로 원본 연결 |
| 14 | 완료 근거 제출·수락 | EQ 충족 근거 제출 → 잠금·검토 대기. 요청자·처리자와 다른 admin이 수락해야 done |
| 16 | 상태 이력 | 상태 바뀔 때 근거·행위자·시각 이력 동시 저장. 이력 저장 실패 → 상태 변경도 취소. 삭제 거부 |
| 18 | 전체 자산 조회 | admin → 전체. member → 자기 것만 |
| 19 | 이력 조회 | admin이 요청 ID로 입력·근거·상태 이력 전체 확인 |
| 21 | 가상 시험 자료 | 정상·빈 값·권한 거부·복구 시험용 최소 자료. 실제 기업의 취약 사실로 보이지 않게 표시 |

**후속(Should·Could) 14개:** FR-04 자산 수정 이력, 09 점수 표시, 10·17 대시보드 카드(요청 목록 필터로 대체), 15 보류 재개, 20 시험 모드, 22 상위 N건, 23 통계, 24 EPSS, 25 묶음 확인, 26 과거 이력, 40 실패 복구, 41 승인 후 취소 확정, 42 완료 무효. 인수 기준은 방향만 정해 두었다.

완료의 증거는 사람이 입력한 업무 기록이다. 앱이 장비에서 적용 사실을 따로 검증한다는 뜻이 아니다.

## 5. 요청 상태와 예외

**상태 흐름:** `submitted → approved → in_progress → done`. 반려는 `rejected`, 취소는 `cancelled`, 일시 보류는 `on_hold`, 착수 후 실패는 `failed`, 완료 뒤 오류 확인은 `invalidated`.

핵심 규칙 네 가지:
1. 반려는 관리자가 거절하는 것, 취소는 신청자가 철회하는 것. 서로 대신 쓰지 않는다.
2. `done`·`failed`·`cancelled`·`invalidated`가 된 요청은 다시 실행하지 않는다. 다시 하려면 이전 요청을 연결한 새 요청과 새 승인을 쓴다.
3. 실제 작업이 실패했다면 복구에 성공해도 같은 ID로 재개하지 않는다.
4. 자산·위험 하나에 활성 요청(`submitted`·`approved`·`in_progress`·`on_hold`)은 하나만 둔다.

**첫 버전에서 실제로 구현하는 것:** 보류는 사유와 재검토일만 기록, 승인 전 취소는 신청자가 직접, 착수 후 실패·포기는 `failed`로 닫고 사유·적용 상태 기록, 완료 후 오류는 정정 메모를 덧붙이기. 나머지 복구·상향 보고·완료 무효 절차는 후속이다.

| 예외 | 상황 | 화면 동작 |
|---|---|---|
| Ex-01·02 | 갱신 실패, 후보 없음 | 이전 정상본·마지막 성공 시각 표시. 후보 0건을 "안전"으로 쓰지 않음 |
| Ex-03 | 오탐, 적용 범위 불명 | 미확인 유지, 자료 보완 후 재검토 |
| Ex-04 | 활성 요청 중복 | 기존 요청 링크 안내, 서버도 차단 |
| Ex-05 | 반려 | 사유 표시, 새 요청으로 다시 작성 |
| Ex-06 | 보류 기한 도래 | "재검토 필요" 표시. 자동 완료·자동 연장 없음 |
| Ex-07 | 권한 밖·잘못된 순서 | 서버가 거부. 버튼 숨김에만 의존하지 않음 |
| Ex-08 | 작성 중 인증·통신 실패 | 저장 완료로 표시하지 않고 내용 보존 |
| Ex-09 | 요청 중 자산 정보 변경 | 신청 당시 값 보존, 차이 표시 |
| Ex-10 | 근거 항목 누락 | 빠진 항목 안내, 입력 유지. 미확인을 성공으로 바꾸지 않음 |

### 완료 근거의 다섯 기준 (EQ)
대상 일치 · 적용 내용(패치·버전 식별자) · 기능 검증(방법·기대값·실제값) · 추적 가능한 자료 · 책임과 시각. 빈 칸은 시스템이, 내용이 충분한지는 admin이 판단한다. 글자만 채운 근거는 수락하지 않는다.

### 적용 여부 확인 순서 (AP)
대상 확보 → 공식 근거 확보 → 대조 → 판정(해당/해당 없음/미확인) → 재검토. 이름이 같다는 이유만으로 영향 버전을 확정하지 않는다. 미확인이면 패치 요청을 막는다.

### 행동별 허용 주체
신청·재신청은 member, 승인·반려는 신청자·처리자와 다른 admin, 착수·결과 제출은 해당 요청의 member, 근거 수락은 신청자·처리자와 다른 admin. 독립 검토할 admin이 없으면 기다린다. 자기 승인 예외는 없다.

## 6. 데이터와 범위

- KEV는 공식 JSON과 공식 미러에서 받는다. EPSS는 선택. NVD 영향 버전 매칭은 첫 버전에 넣지 않는다.
- 판단 순서: 제품 문자열로 후보 제시 → 사람이 적용 범위·현장 제약 확인 → 관리자가 요청 결정. KEV 등재나 점수만으로 자동 확정하지 않는다.
- 보안: 서비스 키는 서버에서만, 행 단위 접근 제어와 서버 검증. 실제 설비·개인정보 사용 안 함.
- 화면: 상태는 색과 글자를 함께, 폰 너비에서도 주요 과업 가능, 큰 버튼, 입력별 오류, 빈 상태.
- 하지 않는 것: 실제 장비 접속, 자동 패치, 호환성 자동 판정, NVD 필수 연동, 자동 알림, 외부 협력사 계정, 다단 승인, 대량 성능 시험.

## 7. 구현 현황과 위험

- 관리자 완료 검토, 자기 승인 금지, 근거 잠금, 실패·취소·정정은 **앞으로 만들 요구**다. 현재 코드의 상태 전이 검사는 member의 `in_progress → done` 허용과 결과 메모 필수 여부만 본다. 실패·취소·무효 상태는 없다.
- **DB 접근 규칙에 결함이 있다.** 담당자 정책이 요청의 모든 열 수정·삭제를 허용해 담당자가 상태를 직접 `done`으로 바꿀 수 있고, 후보 확인 정책에도 열 제한이 없다. FR-02·16은 이를 고친 뒤에만 시험할 수 있다. 수정안 초안은 `05_DB접근규칙_수정안.sql`이며 아직 적용하지 않았다.
- 자산 화면은 자리 표시 수준이고 저장은 메모리 구현이다.
- 공수는 필수 20개 기준 초도 추정이 88~148인시이며, 15개로 줄인 뒤 다시 산정하지 않았다. 실적이 아니다. **확인 필요.**
- 제출 일시(10/27은 임시), 저장소 공개 범위(과제는 비공개 요구, 현재 공개), 문서 7개 방침과 제출 문서 요구의 충돌은 공식 확인 전이다. **확인 필요.**

## 8. 역할 배분 의견

`scripts/ownership.json`의 경로 소유를 기준으로 본 내 의견이다. 팀 협의 전 제안이다.

| 담당 | 영역(소유 경로) | 필수 FR | 의견 |
|---|---|---|---|
| A | 로그인·관리자 화면·공통 화면·Supabase·DB 마이그레이션 | 01·02·18·19 + 16의 저장 | 가장 앞선다. 인증과 DB 접근 규칙이 끝나야 B·C가 실제 저장을 시험할 수 있다. **DB 결함 수정이 첫 일**이다 |
| B | 위험 화면·KEV 수집·매칭·점수 | 05·06·07 + 08의 후보 | 외부 자료와 도메인 규칙이 중심이라 A에 덜 기댄다. 먼저 병렬로 간다. 점수(FR-09)는 후속이니 뒤로 둔다 |
| C | 자산·요청 화면과 요청 상태 규칙·시험 자료·QA | 03·08·11·12·13·14·21 | 필수 중 가장 많고 상태 규칙이 가장 복잡하다. 공수가 한쪽에 쏠릴 위험이 크다 |

- **쏠림:** 필수 15개 중 C가 7개, A가 4~5개, B가 3개다. 14(근거 제출·수락)와 13(승인)은 A의 권한 규칙과 맞물리니 둘이 같이 정해야 한다.
- **제안:** 상태 전이 규칙의 순수 로직은 C가 쓰고, 권한 거부·DB 저장은 A가 맡도록 선을 긋는다. B는 KEV가 끝나면 C의 요청 목록·조회 화면 일부(FR-12·18)를 돕는다. 계약 파일 `ports.ts`는 셋이 함께 리뷰한다.
- 이 배분은 공수와 선행 관계를 실제로 재 본 결과가 아니다. 첫 구현에서 시간을 기록한 뒤 조정한다. **확인 필요.**

## 9. 열린 질문과 가장 작은 검증

| 질문 | 가장 작은 검증 | 결과에 따라 |
