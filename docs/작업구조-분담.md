# 작업 구조와 3명 분담 (시간과 무관하게, 서로 겹치지 않게)

> 작성 2026-10-22 · 연결: [팀-작업계획](팀-작업계획.md)(일정은 참고용) · [spec](../spec.md) · [IA](IA.md) · [ERD](db/erd.md) · [`ports.ts`](../src/application/ports.ts)(계약) · [`scripts/ownership.json`](../scripts/ownership.json)(영역 목록)
> **A=Supabase·Vercel 소유자(기반·관리자·배포), B=데이터·판단, C=입력·요청 흐름·QA.** 이름은 미정.

## 0. 겹치지 않게 하는 원칙 (일정과 상관없이 항상 적용)
1. **한 경로, 한 소유자.** 모든 파일·폴더·화면·표는 정확히 한 사람이 **고친다**. 가져다 쓰는(import·읽기) 것은 누구나 자유다.
2. **서로를 기다리지 않는다.** 각 영역은 계약(`ports.ts`)과 **가짜(fake) 구현**만으로 혼자 끝까지 만들고 시험할 수 있다. 가짜는 이미 `src/infrastructure/container/`에 있다. 상대 구현이 완성되면 조립 파일의 한 줄만 바꾼다.
3. **합쳐지는 곳은 정해져 있다.** 공유 파일은 `ports.ts`와 `domain/types.ts` 둘뿐이고, 바꿀 때는 **제공자와 사용자 둘 다 리뷰**한다.
4. **자동으로 검사한다.** `npm run check:owner -- a|b|c`가 내가 바꾼 파일이 내 영역 안인지 확인한다. 남의 파일을 고치면 실패한다(PR 올리기 전에 실행).
5. **기록도 나눈다.** 작업 로그는 사람별 파일(`docs/작업로그/<날짜>-<a|b|c>.md`)이라 서로 같은 파일을 고치지 않는다. 설계 메모는 `docs/설계/<a|b|c>-내용.md`.

## 1. 시스템 구조 (한 장)
```
 [CISA KEV]                                      [담당자가 입력하는 자산]
    │ ① KEV 가져오기·저장 (B)                        │ ⑥ 자산 등록·수정 (C)
    ▼                                                ▼
 kev_entries ────② 매칭 후보 (B)──────────────── assets
                       ▼
                    matches ─③ 점수·묶음 (B)─▶ 위험 항목 화면 (B) ─④ 확인(해당함/해당 없음) (B)
                       ▼
          ⑤ 호환성 체크리스트 → 패치 요청 (C)
                       ▼
          ⑦ 승인·반려 (A, 관리자 화면 AD-07) ─▶ ⑧ 처리 중→완료/보류/완화 (C) ─▶ 상태 이력
                       ▼
          ⑨ 관리자 열람·데이터 관리·시험 모드 (A)

 바닥: ⓪ 로그인·역할·접근 제한 (A) · DB·접근 규칙 (A) · 공통 화면 틀 (A) · 배포 (A)
```
바통이 넘어가는 곳은 **B→C**(확인된 위험 항목), **C→A**(신청된 요청), **A→C**(승인된 요청)이고, 모두 `ports.ts`의 계약으로 이어진다.

## 2. 코드 구조와 폴더 소유
```
src/domain/           순수 규칙           B: scoring·matching·grouping   C: requestStatus·checklist·history   공유: types
src/application/      사용 절차 + 계약    ports.ts(공유) · risks/(B) · assets/·requests/(C)
src/infrastructure/   DB·외부 연결        supabase/(A) · kev/(B) · seed/(C) · container/(파일별 소유, 아래)
src/components/       화면 부품           common/·AppShell·StatusChip·DataStatusBar(A) · risks/(B) · assets/·requests/(C)
src/app/              화면(경로)          (auth)·(app)/admin(A) · (app)/page.tsx·risks(B) · (app)/assets·requests(C)
supabase/migrations/  DB 표(A가 적용)
tests/unit/           시험                a/ b/ c/ 로 나눔
```
의존은 **안쪽으로만**: `app → application → domain`, `infrastructure`는 계약을 구현한다. `domain`은 아무것도 부르지 않는다.

**조립 파일(`infrastructure/container/`) 소유**: `auth.ts`·`audit.ts`·`index.ts`=A, `kev.ts`·`matches.ts`=B, `assets.ts`·`requests.ts`=C. 각자 자기 파일의 구현만 바꾼다.

## 4. 담당자별 정리

### A — 기반·관리자·배포
- **영역**: 0 로그인·역할·접근 제한, 1 관리자 운영, 2 승인·반려(AD-02·AD-07), 3 DB·배포·발표.
- **계약**: 제공 `CurrentUserProvider`, `AuditLog` / 사용 `RequestRepository`(승인), `KevRepository`(갱신 버튼), 읽기 전용 목록들.
- **이미 있는 것**: 로그인·가입 화면 틀, 관리자 화면 틀 7개, DB 표·RLS·가상 계정, 시드 스크립트.
- **남은 것**: 로그인·가입 연결, 역할 확인과 `/admin` 접근 제한(서버), 관리자 화면에 데이터 연결, 승인·반려, 시험 모드, 배포, 발표.
- **운영 권한**: Supabase·Vercel, 서버 전용 키 보관, DB 변경 적용.

### B — 데이터·판단
- **영역**: 4 KEV 수집·저장, 5 매칭·점수·묶음, 6 위험 항목·대시보드.
- **계약**: 제공 `KevRepository`, `MatchRepository` / 사용 `AssetRepository`(읽기), `RequestRepository`(대시보드 읽기).
- **이미 있는 것**: `scoring`·`matching`·`grouping`·`parseKev` 규칙과 시험, 가짜 저장소, DB에 KEV 1,754개·후보 6,780건.
- **남은 것**: 앱 안에서 KEV를 다시 받아 저장하는 경로(수동·자동), 후보 생성 실행, 위험 항목 화면·확인 입력·묶음 표시, 대시보드 연결, 데이터 출처 카드 완성.

### C — 입력·요청 흐름·QA
- **영역**: 7 자산 관리, 8 패치 요청 흐름, 9 시드·QA.
- **계약**: 제공 `AssetRepository`, `AssetEventRepository`, `RequestRepository` / 사용 `MatchRepository`(확인된 위험 항목), `CurrentUserProvider`.
- **이미 있는 것**: `requestStatus`·`checklist`·`history` 규칙과 시험, 가짜 저장소(요청 흐름 전체 시험 포함), DB에 자산 115·이력 335.
- **남은 것**: 자산·요청 저장소를 Supabase로, 자산 화면(구역·라인 묶기), 체크리스트 신청·중복 방지, 요청 목록·상세·상태 이력, 처리·보류·완화, QA 시트·보고서.

## 6. 일하는 순서 (시간이 아니라 순서)
1. 내 영역의 **가짜 구현으로** 화면과 시험을 먼저 끝낸다(남을 기다리지 않는다).
2. `npm test`, `npm run build`, **`npm run check:owner -- <내 역할>`** 통과.
3. PR(브랜치 `feat/<a|b|c>-내용`) → 작성자 아닌 1명 리뷰 → 머지. `main` 직접 push 금지.
4. 상대 구현이 머지되면 `container/`의 내 파일에서 **가짜를 진짜로 한 줄 교체**한다.
5. `docs/작업로그/<날짜>-<a|b|c>.md`에 한 일 · 결정 · 다음 할 일을 남긴다.
