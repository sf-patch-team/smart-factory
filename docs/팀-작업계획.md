## 1. 어떻게 동시에 하나 (핵심 원칙)
1. **세로로 나눈다.** 각자 "자기 표 + 자기 화면 + 자기 코드 폴더"를 끝까지 맡아서 서로 같은 파일을 거의 만지지 않는다.
2. **계약을 먼저 정해 둔다.** 서로 주고받는 부분은 [`src/application/ports.ts`](../src/application/ports.ts)에 이미 적혀 있다. 상대 구현이 안 끝났어도 그 계약대로 **가짜(fake) 저장소**를 만들어 먼저 개발한다. 계약을 바꿀 때는 그 파일만 작은 PR로 먼저 올리고 단체방에 알린다.
3. **하루 한 번 통합한다.** 매일 밤 정해진 시각에 `main`에 머지하고 서로 받아 합친다.

| | **A** (Supabase·배포 소유자) | **B** (데이터·판단) | **C** (입력·요청 흐름) |
|---|---|---|---|
| 맡은 표 | profiles, app_settings, kev_fetches(운영), audit_log | kev_entries, matches | assets, asset_changes, patch_requests, request_status_history |
| 맡은 화면 | AU-01·02, AD-01~05(06), AD-02 승인 화면 | DB-01, RK-01~05 | AS-01~03, RQ-01~05 |
| 맡은 요구사항 | R-01, 02, 15, 19, 20, 21 | R-05, 06, 07, 08, 09, 10, 23, 25 | R-03, 04, 11, 12, 13, 14, 16, 17, 18, 22, 26(Could) |
| 계약 구현 | `CurrentUserProvider`, `AuditLog` | `KevRepository`, `MatchRepository` | `AssetRepository`, `RequestRepository` |
| 코드 폴더 | `(auth)`, `(app)/admin`, `infrastructure/supabase`, 접근 제한 | `infrastructure/kev`, `domain/scoring·matching`, `(app)/risks`, 대시보드 | `(app)/assets`, `(app)/requests`, `domain/requestStatus·checklist`, 시드 |

## 5. 바이브 코딩 규칙
- **시작:** 각자 `CLAUDE.md`를 읽은 Claude Code로 작업. 요청에 **R-번호·화면 ID**를 넣는다(예: "R-11, RQ-02-P 만들어 줘, 계약은 ports.ts").
- **브랜치:** `feat/<a|b|c>-<내용>`. 하루 1~2개의 작은 PR. **PR 조건:** `npm test`·`npm run build` 통과 + 작성자 아닌 1명 리뷰. `main` 직접 push 금지.
- **공유 파일**(`globals.css`, `AppShell.tsx`, `domain/types.ts`, `ports.ts`, 마이그레이션)은 한 사람이 소 PR로 먼저 올린다.
- **DB 변경:** 마이그레이션 SQL 파일을 PR로 올리면 **A가 확인하고 적용**한다(A의 Supabase 계정). 번호는 `0002_…`부터 순서대로, 겹치면 늦게 올리는 사람이 고친다.
- **비밀:** A가 `.env.local`의 **공개용 값**(URL·anon 키)만 팀원에게 개인 전달한다. **서버 전용 키(service role)와 CRON_SECRET은 A만** 갖고 팀원에게 주지 않는다. 채팅·PR·스크린샷·저장소에 값을 남기지 않는다.
- **AI가 만든 코드:** 돌려 보고 시험을 같이 만든다(성공 기준 번호마다 1건 이상). 새 라이브러리는 먼저 묻는다.
- **동기화:** 아침 10분(오늘 할 것/막힌 것), 밤 22시 통합 머지. 30분 막히면 바로 공유.
- **서류:** 만든 기능은 `Intent.md` "결과"를 같은 PR에서 갱신한다.
