# PRD: smart-factory (자산 취약점 패치 관리)
상태: 초안 | 작성일: 2026-10-22 | 마감: 2026-10-27(화) | 연결 문서: [IA](IA.md) · [UJ](UJ.md) · [인터뷰 가설](01-momtest-인터뷰.md) · [ADR](adr/) · [GLOSSARY](../GLOSSARY.md)

## 1. 요약
공장 설비와 IT 자산을 담당하는 사람이, **실제 악용 중인 취약점(KEV) 중 우리 자산에 해당하는 것**을 우선순위와 함께 보고, 호환성 확인을 거쳐 패치를 요청·승인·기록하는 웹앱이다. 설비는 "지금 패치 못 함"이 흔해서 보류·완화 조치도 정식 경로로 둔다. 지금 만드는 이유는 팀 프로젝트 마감(10/27)과, 우선순위를 못 정하고 기록이 흩어진다는 문제가 조사에서 반복돼서다.

## 3. 배경
- **문제와 근거**: 노후 설비·수기 기록, 시스템 간 연동 부족(조사: koreascience·automation.com·moxa), 알람이 많아 무시됨(조사: APM Digest·벤더 설문). 패치 병목이 "판단·확인·승인 대기"라는 점은 **가상 페르소나 인터뷰 가설**이다(실제 확인 전, `01` 문서 5번).
- **데이터 사실(직접 확인, 2026-10-22)**: KEV 1,754개, 대부분 `dueDate`가 이미 지남, 산업 제어 벤더는 4개뿐(`00` 문서). → 점수는 "기한 초과 일수" 중심, 가상 자산은 IT·네트워크 중심.
- **왜 지금**: 과제 마감과 필수 조건 7개(`CLAUDE.md`)를 5일 안에 충족해야 한다.

## 4. 목표와 지표
- **목표**: 어떤 자산이 지금 위험하고 무엇부터 해야 하는지 5분 안에 알고, 모든 조치를 근거와 함께 기록한다.
- 아래 목표값은 **시험 데이터 기준 가정**이며, 실사용 수치가 아니다.

| 지표 | 현재 | 목표 | 기한 | 측정 방법 |
|---|---|---|---|---|
| 필수 CUJ 1~5 시험 통과 | 0/5 | 5/5 | 10/26 | 자동·수동 QA |
| 상태 변경 중 이력(시각·행위자·사유) 남은 비율 | - | 100% | 10/26 | 시험 데이터 검증 |
| 후보 확인율(24시간 내) | 측정 전 | 80% | 추후 | 이력 기준 |
| 요청→완료 소요 시간 | 측정 전 | 계산 가능 상태 | 10/26 | 이력의 시각 차이 |
| 과제 필수 키워드 7개 구현 | 0/7 | 7/7 | 10/26 | 6번 대응표 |

## 5. 사용자 세그먼트

|---|---|---|---|
| **담당자**(설비·제어, IT 인프라) | 해당 여부를 눈으로 대조, 우선순위 기준 없음, 점검 창·벤더 승인 대기 | 가동 중 작업 불가, 패치 호환성 불확실 | 인터뷰 P1·P2·P6(가설) |

## 6. 가치 제안
### 담당자
- **Who**: 설비·IT 자산을 맡은 담당자 · **Why**: 우리 장비에 해당하는 위험을 빨리 가려 안전하게 조치하고 싶다
- **What before**: 공지 여러 경로 확인, 엑셀과 눈으로 대조, 벤더에 메일로 문의, 기록은 메일에 흩어짐
- **How**: 자산과 KEV를 대조해 후보를 만들고, 담당자가 확인하며, 점수와 근거를 보여 주고, 호환성 체크리스트로 신청한다
- **What after**: 상위 위험 5건을 한 화면에서 보고, 못 하는 건 사유와 재검토일을 남겨 정식 승인받는다
- **Alternatives**: 엑셀+메일, 일반 티켓 도구. 우리는 취약점 매칭과 호환성 확인, 보류 경로가 한곳에 있다
- **한 줄**: "우리 자산 중 지금 위험한 것과 그 이유를 한 화면에서 보고, 근거를 남기며 조치합니다."

### 관리자
- **Who**: 보안·결재 담당 · **Why**: 승인 근거를 보고 빠르게 결정하고 감사 증적을 확보하고 싶다
- **What before**: "취약합니다"만 있는 요청, 이력은 메일·메신저에 흩어짐
- **How**: 요청마다 점수 구성·영향 설비·호환성 확인 결과를 보여 주고 모든 상태 이력을 저장한다
- **What after**: 근거를 보고 승인·반려하며 기간·사용자별로 이력을 바로 연다
- **Alternatives**: 엑셀·메일·티켓 도구
- **한 줄**: "근거 있는 요청만 받고, 누가 언제 왜 했는지 한 번에 확인합니다."

## 7. 핵심 사용자 여정(CUJ)과 사용자 스토리
| CUJ | 유형 | 사용자 스토리 | 성공 기준 | MOT |
|---|---|---|---|---|
| CUJ-1 위험 발견·확인 | Traffic | 담당자로서 내 자산 중 위험한 것을 가려내기 위해 후보를 확인하고 싶다 | 후보가 위험 항목으로 확정 | 점수 구성 이해, 확인 입력 |
| CUJ-2 요청→완료 | OEC | 담당자로서 승인 받아 안전하게 조치하고 기록하고 싶다 | 상태가 완료 + 결과 입력 | 체크리스트, 승인 |
| CUJ-3 보류·완화 | OEC | 담당자로서 패치할 수 없을 때 사유·대안으로 예외 승인받고 싶다 | 사유·재검토일과 함께 승인 | 사유 입력, 승인 |
| CUJ-4 감사 열람 | OEC | 관리자로서 모든 조치의 누가·언제·왜를 보고 싶다 | 필터로 이력 열람 | 필터 조회 |
| CUJ-5 데이터 신뢰 | Traffic | 사용자로서 위험 정보가 최신인지 믿고 싶다 | 받은 시각·상태 표시 | 갱신 실패 표시 |

인수 기준 예(CUJ-2): **Given** 확인된 위험 항목 **When** 담당자가 체크리스트를 채워 신청하고 관리자가 승인하고 담당자가 결과를 입력하면 **Then** 상태는 완료이고 상태 이력에 4건의 기록(시각·행위자·사유)이 남는다.

### 8.3 비기능 요구사항
- **보안**: API 키·Supabase 서비스 키는 서버 환경변수에만. 행 수준 보안(RLS)으로 담당자는 자기 자산·요청만, 관리자는 전체. 비밀번호는 평문 저장 금지.
- **개인정보**: 가상 인물·가상 메일만 쓴다. 앱은 AI 서비스에 어떤 데이터도 보내지 않는다.
- **성능**: 주요 화면 2초 안에 열림(가상 데이터 기준).
- **접근성·화면**: 상태는 색 + 글자로 표시, 라이트/다크, 폰 너비에서 가로 스크롤 없음, 큰 버튼. 쉬운 한국어 문구.
- **데이터 신선도**: 받은 시각을 항상 표시.
