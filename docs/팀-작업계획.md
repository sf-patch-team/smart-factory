## 5. 바이브 코딩 규칙 (3명이 같은 방식으로)
- **시작:** 각자 `CLAUDE.md`를 읽은 Claude Code로 작업한다. 요청할 때 **spec의 R-번호와 화면 ID**를 넣는다(예: "R-11, RQ-02-P 만들어 줘").
- **브랜치:** `feat/<역할>-<내용>` (예: `feat/b-kev-fetch`). 하루 1~2개의 **작은 PR**. 큰 덩어리를 한 번에 올리지 않는다.
- **PR 조건:** `npm test`와 `npm run build` 통과, 작성자가 아닌 1명이 리뷰, 머지는 리뷰 후. `main` 직접 push 금지.
- **AI가 만든 코드:** 돌려 보고 시험을 같이 만든다(spec 성공 기준 번호마다 시험 1건 이상). 새 라이브러리는 먼저 묻는다.
- **비밀:** Supabase 키 등은 각자 대시보드에서 직접 복사해 `.env.local`에 넣는다. 채팅·저장소·PR·스크린샷에 값을 남기지 않는다.
- **동기화:** 매일 아침·밤 10분(오늘 할 것 / 막힌 것). 막히면 30분 안에 공유한다.
- **서류:** 만든 기능은 `Intent.md` "결과"와 필요하면 spec·plan을 같은 PR에서 고친다(코드에 숨기지 않는다).

## 6. 막힐 수 있는 곳과 대비
| 위험 | 대비 |
|---|---|
| Supabase 만들기 승인 지연 → 모두 막힘 | 오늘 밤 승인. 늦어지면 B·C는 **저장소 인터페이스 + 시드 데이터**로 먼저 개발하고 나중에 DB로 교체 |
| 같은 파일 충돌 | 2번 공유 파일 규칙, 작은 PR, 매일 `main`을 받아 합치기 |

| 인터뷰를 못 함 | 발표에서 "가상 페르소나 가설"이라고 정직하게 말하고, 가능한 만큼만 기록 |
| 키 노출 | 5번 비밀 규칙, 커밋 전 검색 |
