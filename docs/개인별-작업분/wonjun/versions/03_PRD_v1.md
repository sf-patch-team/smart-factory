## 1. 문제 문장

- 내가 고른 후보: **A 조치 이행 확인의 단절**
- 문제 문장: IT·보안 담당자는 취약점 패치를 현장에 요청하고 완료 회신을 받을 때, 회신에 어떤 장비에 무엇을 했는지 근거가 없어 장비마다 요청·대장·작업 기록을 다시 대조하느라 시간과 누락 위험을 본다. 지금은 엑셀·사내 게시판·메일·전화로 버틴다.
- 고른 이유: 요건의 일곱 가지(로그인, DB, 관리자 페이지, 실시간 데이터, 직접 입력, 관리자 확인, 요청과 반응)를 한 요청 흐름으로 이을 수 있는 문제다. 다른 후보(B 예외 조치의 추적 공백, C 보안 작업과 생산 일정의 충돌)는 이 문제를 처리하는 예외·입력 조건으로 다룬다.
- **확인 필요:** 얼마나 자주 생기는지, 손실이 얼마인지는 측정한 적이 없다. 모든 현장에서 가장 큰 문제라고 주장하지 않는다.

## 2. 5 Whys (3번까지)

모두 가설이며 인터뷰 근거가 없다. **확인 필요**(검증 안 됨).

- 문제: 완료 회신을 받아도 실제 조치 여부를 장비마다 다시 확인해야 한다
- 왜1: 회신에 어떤 장비에 무엇을 적용했고 어떻게 확인했는지 근거가 없다
- 왜2: 회신 형식이 사람마다 달라 정해진 틀이 없고, 요청·회신이 메일·게시판·엑셀에 흩어져 자산 목록과 연결되지 않는다
- 왜3: "무엇을 근거로 완료로 볼지"의 기준과 승인 규칙이 정해져 있지 않다

## 3. 목표 (한 문장)

- 목표: **새 보안 공지가 들어오면 영향 받을 수 있는 장비를 찾아 확인하고, 패치 요청이 어떤 근거로 완료됐는지를 장비 단위로 한곳에서 볼 수 있게 한다.**

## 4. 핵심 키워드 7개, 우리 앱에서 어떻게?

- 로그인: Google 로그인. 첫 로그인은 요청자·처리자 역할(member). 승인·검토는 admin. 시스템 관리자 역할은 후속(**확인 필요**)
- DB: Supabase. 자산, 취약점 후보, 요청, 상태 이력, 완료 근거를 저장. 행 단위 접근 제어(현재 접근 규칙에 결함이 있어 수정이 먼저. **확인 필요**: 수정 SQL 적용 승인)
- 관리자 페이지: 전체 자산·요청·상태 이력 조회, 승인·반려, 완료 근거 수락, 데이터 갱신 실행·기록
- 실시간 데이터 받기: 수집기가 CISA KEV를 주기적으로 가져와 받은 시각·성공/실패를 표시. 새로 등록된 항목이 "새 공지"
- 직접 입력: 가상 자산(제품·펌웨어·위치·담당자), 적용 여부 확인, 요청, 완료 근거
- 관리자 확인: 요청자·처리자와 다른 관리자가 승인·반려하고 완료 근거를 수락. 협력사·타 팀 승인이 필요한 요청은 그 기록을 확인
- 요청과 반응: 신청 → 승인/반려 → 처리 중 → 완료(근거). 단계마다 이력이 쌓이고 순서를 건너뛸 수 없다

## 5. 하지 않을 것 (2개 이상)

1. 실제 장비에 접속하거나 패치를 자동 적용하지 않는다 — 기록과 판단 지원까지만. 실제 장비 쓰기는 안전·보안 위험이 크다.
2. 호환성·영향 여부를 자동 판정하지 않는다 — 제품명 표기가 제각각이고 공지 형식이 일정하지 않아 3일 안에 믿을 만하게 만들 수 없다. 사람이 확인한다.
3. NVD 영향 버전 매칭, EPSS, 제조사 공지 자동 수집은 첫 버전에서 하지 않는다 — 범위를 지키기 위해 후속으로 둔다.
4. 자동 알림, 협력사 계정, 다단 승인은 하지 않는다 — 협력사·타 팀 승인은 신청자가 기록하는 최소형으로 시작한다.
5. 실제 회사의 자산·개인정보를 쓰지 않는다 — 가상 자료만 쓴다.

## 6. 데이터

- **받아 올 것**
    - KEV: 실제 악용이 확인된 취약점 목록. 새 항목(`dateAdded`)이 긴급 확인의 출발점이다. 쓰는 곳: 위험 목록 화면, 장비 후보 매칭. 공개 JSON이라 키가 필요 없다. 갱신 주기와 저장 위치(Supabase 표), 실패 시 이전 정상본 유지 방식은 **확인 필요**
    - NVD: 첫 버전 제외. 제품명·버전 표기가 제각각이라 매칭이 가장 어렵다. **확인 필요**(후속)
    - EPSS: 첫 버전 제외. 쓰게 되면 수집기가 공지 시점에 가져오는 우선순위 참고값이고, 값이 없으면 0점으로 대신하지 않는다
    - 제조사 보안 공지(PLC·네트워크 장비): 첫 버전은 담당자가 공지 링크와 영향 범위 원문을 붙여 넣는 칸만 둔다. 자동 수집 방식·이용 조건은 **확인 필요**
- **회원이 직접 넣을 것** (가상 자산):
    - 제조사, 제품(모델), 펌웨어·소프트웨어 버전(모르면 "미상"), 도입 연도, 위치(공장·라인·구역·망), 담당자, 중요도, 작업 제약(`vendor_approval`, `no_downtime`, `maintenance_window` 등)
    - **자산 목록에는 공지·CVE를 넣지 않는다.** 공지와의 연결은 공지가 들어온 시점의 매칭 결과로만 생긴다.
    - 시험용 데이터셋은 `dataset-v2`(자산 데이터)이고, 수집기 결과를 비교하는 정답지는 자산 목록과 별개의 시험 자료다. 상세는 `07_데이터셋_v2_변경내역.md`

## 7. 요청 흐름 (단계별 한 줄)

| 단계 | 누가 | 화면에서 하는 일 | 막아야 할 것 |
| --- | --- | --- | --- |
| 신청 | 요청자(member) | 후보 장비를 확인(적용 여부)하고 적용 확인·시험 기준·복구 계획을 적어 신청. 외부 승인이 필요한 장비는 승인 대상·상태·증빙을 기록 | 남의 자산 신청, 적용 미확인 상태 신청, 같은 장비·위험의 활성 요청 중복 |
| 승인 / 반려 | 관리자(admin) | 근거와 외부 승인 기록을 확인해 승인하거나 사유를 적어 반려 | 신청자·처리자와 같은 사용자의 승인, 사유 없는 반려, 외부 승인 항목이 빠진 상태의 승인 |
| 처리 중 | 처리자(member) | 작업 후 적용 내용·검증 결과를 입력하고 근거를 제출(제출본 잠금) | 승인 전 착수, 다른 사람의 대리 처리, 근거 항목 누락 |
| 완료 | 관리자(admin) | 제출 근거를 검토해 수락하면 완료, 부족하면 보완 요구 | 수락 없이 완료, 요청자·처리자 본인의 수락, 낡은 제출본으로 완료 |

- 첫 버전의 요청 상태는 `submitted → approved → in_progress → done`과 반려 `rejected` 다섯 개다. 보류·취소·실패·완료 무효는 후속이다(`03a_PRD_보충.md` 5절).
- **협력사·내부 타 팀 승인(제안, 팀 미채택):** 협력사 승인은 공급사 보증·검증이 필요한 장비(`vendor_approval`), 내부 타 팀 승인은 가동을 멈추는 작업(`no_downtime`, `maintenance_window`)에서 필요하다. 요청 화면이 장비의 작업 제약으로 필요 여부를 미리 알려 주고, 신청자가 승인 대상·상태·일시·증빙 메모를 기록한다. 신청자가 직접 입력하므로 증빙 요약일 뿐이며, admin이 승인 때 확인하고 하나라도 빠졌거나 거절이면 서버가 내부 승인을 막는다. 외부 승인이 내부 승인을 대신하지는 않는다. **확인 필요:** 협력사 승인을 앱에서 직접 받을지, 어느 팀까지 요구할지, 요구 여부를 자산 제약으로 자동 정할지(`03a_PRD_보충.md` 10-1절).
- **시스템 관리자(제안):** 첫 버전은 member·admin 둘이고, 시스템 관리는 Supabase 소유자의 수동 작업으로 처리한다. 앱 안의 시스템 관리자 역할은 후속이며 만든다면 요청 승인·완료 검토를 못 하게 해 업무 승인과 시스템 설정을 분리한다. **확인 필요.**

## 8. 판단 (배점 15점)

- 보는 값: KEV 새 등재 항목의 제조사·제품 문자열, 장비의 제품·펌웨어·버전, 장비의 작업 제약·중요도, 받은 시각
- 내는 판단:
    1. 새 KEV 항목의 제품 문자열이 장비의 제품과 비슷하면 그 장비를 **후보(`candidate`)**로 만든다.
    2. 담당자가 공식 자료로 버전·구성을 확인해 `confirmed`(해당) / `dismissed`(해당 없음) / 미확인으로 판정한다. 확인하지 못한 항목은 미확인으로 남겨 요청을 막는다.
    3. 확인된 장비는 공유하고 필요하면 패치 요청 흐름으로 넘긴다.
- 화면에 보일 근거: "KEV 등재일, 받은 시각, 매칭된 제품 문자열, 장비의 버전, 공지 링크, 판정자·판정 시각". 후보는 취약 확정이 아니라고 표시하고, 가상 자산 기준의 시험 결과임을 표시한다.
- 이 데이터로는 알 수 없는 것:
    - 실제 장비가 공격에 노출돼 있는지
    - 패치가 실제로 적용됐는지 — 완료는 사람이 입력한 기록일 뿐 앱이 장비에서 확인한 것이 아니다
    - 패치가 생산에 미칠 영향과 호환성
    - 제품명 표기가 달라 생기는 누락·오탐. 버전이 비어 있거나 공지 범위가 계열 단위면 **확인 필요**로 남는다
    - KEV에 없는 취약점이 악용되고 있는지
