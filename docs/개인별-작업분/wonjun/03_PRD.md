

## 0. 가져온 것 · 바꾼 것 · 버린 것

| 구분 | 내용 | 이유 |
|---|---|---|
| 가져온 것 | FR·Ex·EQ·AP 번호와 각 규칙의 핵심 뜻, 요청 상태 이름 | 팀 문서와 번호가 달라지면 비교가 안 된다 |
| **바꾼 것(중요)** | **팀 PRD의 Must 20개를 15개로 줄였다. 강등한 5개: FR-15 보류 재개, FR-20 시험 모드, FR-40 작업 실패 복구, FR-41 승인 후 취소 확정, FR-42 완료 무효.** 이 5개는 팀 PRD에서 필수다 | 3일·3인 안에 20개는 어렵다고 보았다. 잃는 것: 작업 실패·취소·완료 정정을 기록하는 경로(첫 버전은 그런 요청을 처리할 수 없다), 외부 실패를 일부러 만들어 보는 시험 수단. **이 강등은 내 제안이며 팀 합의가 필요하다** |
| 바꾼 것 | 문장을 모두 새로 썼다. 필수 요구 15개만 본문에 두고 후속은 한 표에 모았다. 인수 기준은 "입력 → 기대 결과" 한 줄로 줄였다. 시험 현황은 한 문장으로 합쳤다 | 한 번에 읽히는 분량으로 줄이면 팀원과 다른 점이 눈에 띈다 |
| 바꾼 것 | 요청 상태를 "첫 버전 5개 / 후속"으로 갈랐다(5절) | 3일 안에 끝낼 범위를 먼저 정하려고 |
| 버린 것 | 공수 표 8행 상세, 과제 조건 원문 대조표, 같은 ID 재개 경계의 사례 표, 최초 관리자 지정 5단계의 세부 | 통합 초안에 남아 있어 중복이다. 필요하면 해당 절을 찾아 읽는다 |
| 버린 것 | "이미 확인했다"는 식의 구현 현황 주장 | 이 문서는 요구를 말할 뿐 동작 확인 자료가 아니다 |

## 1. 한 장 요약

- **무엇을:** 공장 자산의 취약점 조치를 요청 → 승인 → 처리·근거 제출 → 관리자 검토까지 한 요청에 묶어 기록하는 웹앱.
- **누가:** 요청하고 처리하는 담당자(member), 승인하고 근거를 검토하는 관리자(admin).
- **아닌 것:** 패치를 대신 실행하는 도구가 아니다. 장비에 접속하지 않고, 호환성을 자동 판정하지 않는다.
- **문제(가설):** 완료 회신이 와도 어느 자산에 무엇을 적용했는지, 어떻게 확인했는지가 요청과 이어지지 않아 기록을 다시 맞춰 봐야 할 수 있다. 얼마나 자주 생기는지, 손실이 얼마인지는 재 본 적이 없다. **확인 필요.** 
- **현재 상태:** 앱과 DB 기준 시험은 아직 한 번도 돌리지 않았다. 도메인 규칙과 가짜 저장소 단위 시험 50건만 통과했다.

## 2. 사용자

| 역할 | 하는 일 | 지금의 불편(가설) → 우리가 주는 것 |
|---|---|---|
| member | 자산 등록, 요청 작성, 처리, 근거 제출 | 요청·대장·메일을 따로 대조 → 요청 하나에서 다음 행동과 근거 확인 |
| admin | 승인·반려, 근거 수락, 전체 조회 | 부서별 회신 취합 → 전체 목록·결과·보류 사유·이력 조회 |

- 첫 버전은 신청자와 처리자를 같은 member로 보고, 승인·검토는 반드시 다른 admin이 한다.
- 새 "검증자" 역할은 만들지 않는다. 역할 관리 화면, 협력사 계정, 다단 승인은 범위 밖이다.
- 이 사용자 설명은 팀의 가정이다. 실제 현장 담당자에게 확인한 것이 아니다. **확인 필요.**

| 담당자의 확인 부담 | 자료 없음 | 첫 버전 밖. 실사용자 검증 뒤 측정 |

## 4. 첫 버전 필수 요구 15개

입력 → 기대 결과로 적는다. QA 번호는 `QA-FR-번호`.

| FR | 요구 | 입력 → 기대 결과 |
|---|---|---|
| 01 | Google 로그인 | 첫 로그인 → member 생성. 재로그인 → 같은 계정. 취소·실패 → 비로그인 |
| 02 | 권한 분리 | 남의 자산 조회, 자기 요청 상태 직접 변경, 자기 역할 변경, 자기 요청 승인 → 모두 서버·DB가 거부 |
| 03 | 자산 입력 | 이름·벤더·제품·버전(모르면 미상)·담당자 → 저장 후 같은 값 조회. 필수 누락 → 거부 |
| 05 | KEV 갱신 | 관리자가 갱신 → 저장 후 개수 일치. 외부 실패 → 이전 정상본 유지·실패 표시 |
| 06 | 수신 상태 표시 | 정상 → 값과 받은 시각. 0건 → "내용 없음". 실패 → "못 읽음"과 마지막 성공 시각 |
| 07 | 후보 제시 | 벤더·제품이 비슷한 자산–KEV 쌍 → 후보로 저장. 후보만으로 "취약 확정" 표시 안 함 |
| 08 | 적용 여부 확인 | 담당자가 해당/해당 없음 선택 → 판단자·시각·공식 자료 저장. 근거 부족 → 미확인 유지 |
| 11 | 요청 작성 | 적용 확인·시험 기준·복구 계획 입력 → 신청 당시 자산 정보와 함께 저장. 같은 자산·위험의 활성 요청 있으면 거부 |
| 12 | 내 요청 조회 | 상태와 다음 행동 표시. 없음과 조회 실패를 구분 |
| 13 | 승인·반려 | 다른 사용자인 admin 승인 → approved. 반려는 사유 필수. 재신청은 새 ID로 원본 연결 |
| 14 | 완료 근거 제출·수락 | EQ 충족 근거 제출 → 잠금·검토 대기. 요청자·처리자와 다른 admin이 수락해야 done |
| 16 | 상태 이력 | 상태 바뀔 때 근거·행위자·시각 이력 동시 저장. 이력 저장 실패 → 상태 변경도 취소. 삭제 거부 |
| 18 | 전체 자산 조회 | admin → 전체. member → 자기 것만 |
| 19 | 이력 조회 | admin이 요청 ID로 입력·근거·상태 이력 전체 확인 |
| 21 | 가상 시험 자료 | 정상·빈 값·권한 거부·복구 시험용 최소 자료. 실제 기업의 취약 사실로 보이지 않게 표시 |

**팀 PRD에서 Must였다가 내린 5개:** FR-15 보류 재개, FR-20 시험 모드, FR-40 작업 실패 복구, FR-41 승인 후 취소 확정, FR-42 완료 무효. 영향은 0절 참조.

**원래 Should·Could 9개(후속):** FR-04 자산 수정 이력, 09 점수 표시, 10·17 대시보드 카드(요청 목록 필터로 대체), 22 상위 N건, 23 통계, 24 EPSS, 25 묶음 확인, 26 과거 이력. 인수 기준은 방향만 정해 두었다. (FR-24 EPSS는 첫 버전에 넣지 않음, 10-2절)

**시험 가능하게 만드는 최소 기준(위 표를 보완):**
- FR-14: EQ 5칸이 모두 비어 있지 않으면 제출 가능, 하나라도 비면 서버가 거부한다. 내용이 충분한지는 admin이 판단하며 자동 판정이 아니다. 신청자·처리자와 같은 사용자가 수락하면 거부한다.
- FR-06: 정상·0건·실패 세 상태는 외부 수집 주소를 환경변수로 바꾸거나 일부러 잘못된 주소를 넣어 만든다(시험 모드가 후속이라 이 방법을 쓴다).
- FR-12: "없음"은 정상 응답의 빈 목록, "조회 실패"는 오류 응답으로 구분한다.
- FR-02: 시험 계정은 member 1명 이상과 admin 1명 이상이다. 같은 admin이 승인과 완료 검토를 모두 해도 된다(신청자·처리자가 member로 다르기 때문). 거부 지점은 화면이 아니라 서버·DB 정책 양쪽이다.

완료의 증거는 사람이 입력한 업무 기록이다. 앱이 장비에서 적용 사실을 따로 검증한다는 뜻이 아니다.

## 5. 요청 상태와 예외

**첫 버전 상태(5개):** `submitted → approved → in_progress → done`, 그리고 반려 `rejected`. 시험 가능한 상태는 이 5개뿐이다.

**후속 상태(첫 버전에는 화면·저장 모두 없음, 요구 번호는 FR-15·40·41·42):** 일시 보류 `on_hold`, 취소 `cancelled`, 착수 후 실패 `failed`, 완료 뒤 오류 확인 `invalidated`. 첫 버전에서 작업이 실패하거나 취소해야 하면 앱에 기록할 방법이 없고 메모로만 남긴다. 이는 팀 PRD(Must)와 다르다.

핵심 규칙 네 가지:
1. 반려는 관리자가 거절하는 것, 취소는 신청자가 철회하는 것. 서로 대신 쓰지 않는다.
2. `done`·`failed`·`cancelled`·`invalidated`가 된 요청은 다시 실행하지 않는다. 다시 하려면 이전 요청을 연결한 새 요청과 새 승인을 쓴다.
3. 실제 작업이 실패했다면 복구에 성공해도 같은 ID로 재개하지 않는다.
4. 자산·위험 하나에 활성 요청(`submitted`·`approved`·`in_progress`·`on_hold`)은 하나만 둔다.

**후속 규칙의 요약(구현하지 않음):** 보류는 사유와 재검토일, 승인 전 취소는 신청자 직접, 착수 후 실패·포기는 `failed`로 닫고 사유와 적용 상태 기록, 완료 후 오류는 정정 메모. 복구·상향 보고·완료 무효 절차도 후속이다.

| 예외 | 상황 | 화면 동작 |
|---|---|---|
| Ex-01·02 | 갱신 실패, 후보 없음 | 이전 정상본·마지막 성공 시각 표시. 후보 0건을 "안전"으로 쓰지 않음 |
| Ex-03 | 오탐, 적용 범위 불명 | 미확인 유지, 자료 보완 후 재검토 |
| Ex-04 | 활성 요청 중복 | 기존 요청 링크 안내, 서버도 차단 |
| Ex-05 | 반려 | 사유 표시, 새 요청으로 다시 작성 |
| Ex-06 | 보류 기한 도래(보류는 후속) | "재검토 필요" 표시. 자동 완료·자동 연장 없음 |
| Ex-07 | 권한 밖·잘못된 순서 | 서버가 거부. 버튼 숨김에만 의존하지 않음 |
| Ex-08 | 작성 중 인증·통신 실패 | 저장 완료로 표시하지 않고 내용 보존 |
| Ex-09 | 요청 중 자산 정보 변경 | 신청 당시 값 보존, 차이 표시 |
| Ex-10 | 근거 항목 누락 | 빠진 항목 안내, 입력 유지. 미확인을 성공으로 바꾸지 않음 |

### 완료 근거의 다섯 기준 (EQ)
대상 일치 · 적용 내용(패치·버전 식별자) · 기능 검증(방법·기대값·실제값) · 추적 가능한 자료 · 책임과 시각. 빈 칸은 시스템이, 내용이 충분한지는 admin이 판단한다. 글자만 채운 근거는 수락하지 않는다.

### 적용 여부 확인 순서 (AP)
대상 확보 → 공식 근거 확보 → 대조 → 판정(해당/해당 없음/미확인) → 재검토. 이름이 같다는 이유만으로 영향 버전을 확정하지 않는다. 미확인이면 패치 요청을 막는다.

### 행동별 허용 주체
신청·재신청은 member, 승인·반려는 신청자·처리자와 다른 admin, 착수·결과 제출은 해당 요청의 member, 근거 수락은 신청자·처리자와 다른 admin. 신청자·처리자는 member이므로 admin 한 명이 승인과 완료 검토를 모두 해도 된다. admin이 자기 요청을 신청·처리하는 경우는 첫 버전에 없고, 그때 다른 admin이 없으면 기다린다(자기 승인 예외 없음).

## 6. 데이터와 범위

- KEV는 공식 JSON과 공식 미러에서 받는다. 저장 위치(Supabase 테이블)와 갱신 방식(관리자가 수동 갱신, 성공했을 때만 기존 값을 교체하고 실패하면 이전 정상본 유지)은 **확인 필요**한 제안이다. 서버 전용 키로만 쓴다. EPSS는 선택(CVE 번호로 KEV와 연결). NVD 영향 버전 매칭은 첫 버전에 넣지 않는다.
- 판단 순서: 제품 문자열로 후보 제시 → 사람이 적용 범위·현장 제약 확인 → 관리자가 요청 결정. KEV 등재나 점수만으로 자동 확정하지 않는다.
- 보안: 서비스 키는 서버에서만, 행 단위 접근 제어와 서버 검증. 실제 설비·개인정보 사용 안 함.
- 화면: 상태는 색과 글자를 함께, 폰 너비에서도 주요 과업 가능, 큰 버튼, 입력별 오류, 빈 상태.
- 하지 않는 것: 실제 장비 접속, 자동 패치, 호환성 자동 판정, NVD 필수 연동, 자동 알림, 외부 협력사 계정, 다단 승인, 대량 성능 시험.

## 7. 구현 현황과 위험

- 관리자 완료 검토, 자기 승인 금지, 근거 잠금, 실패·취소·정정은 **앞으로 만들 요구**다. 현재 코드의 상태 전이 검사는 member의 `in_progress → done` 허용과 결과 메모 필수 여부만 본다. 실패·취소·무효 상태는 없다.
- **DB 접근 규칙에 결함이 있다.** 담당자 정책이 요청의 모든 열 수정·삭제를 허용해 담당자가 상태를 직접 `done`으로 바꿀 수 있고, 후보 확인 정책에도 열 제한이 없다. FR-02·16은 이를 고친 뒤에만 시험할 수 있다. 수정안 초안은 `05_DB접근규칙_수정안.sql`이며 아직 적용하지 않았다.
- 자산 화면은 자리 표시 수준이고 저장은 메모리 구현이다.
- 공수: 팀 PRD의 초도 추정은 필수 20개 기준 88~148인시(예비 포함)이다. 15개로 줄인 뒤 다시 산정하지 않았다. 거친 계산으로 근거 버전·예외 규칙 묶음(20~32시간)을 빼면 55~110인시, 3인이면 1인당 약 18~37시간이다. 이 계산은 근거 없는 감산이므로 **확인 필요**하고, 3일 안에 15개 전부를 보장하지 못한다. 10절의 새 소스·역할은 공수에 들어 있지 않다. FR-16(상태와 이력을 한 번에 저장, 실패 시 취소)은 DB 트랜잭션과 접근 정책이 필요해 가장 어렵다.

## 10. 확장 제안 — 권한 · 데이터 소스 (팀 협의 필요)

통합 초안에 아직 없거나 약하게만 있는 내용을 내 기준으로 정리한 제안이다. 채택 전에는 범위·공수가 정해지지 않았다.

### 10-1. 시스템 관리 권한과 협력사·내부 타 팀 승인 (제안, 팀 미채택)

**시스템 관리자**

- 지금 PRD: 최초 admin은 Supabase 소유자가 수동 지정하고, 데이터 갱신(FR-05)은 admin이 실행한다.
- 첫 버전: 앱 역할은 member·admin 둘로 두고, 시스템 관리는 소유자의 수동 작업으로 처리한다. 데이터 갱신은 FR-05의 수동 갱신만 둔다(정기 갱신은 후속).
- Should, 미설계: 앱 안의 시스템 관리자 역할. 만든다면 요청 승인·완료 검토를 할 수 없게 해서 업무 승인과 시스템 설정을 분리한다.

**협력사·내부 타 팀 승인이 필요한 경우**

패치는 우리 팀의 승인만으로 끝나지 않는 경우가 있다. 필요하면 요청에 이를 넣어야 한다.

| 경우 | 누가 승인하나 | 예 |
|---|---|---|
| 협력사(외부) 승인 | 설비·소프트웨어 공급사 | 제조사 보증이나 유지보수 계약상 펌웨어를 임의로 올리면 안 되는 장비, 공급사 검증이 필요한 MES·SCADA 서버 |
| 내부 타 팀 승인 | 생산·설비·보안·IT 운영 등 다른 팀 | 가동을 멈춰야 하는 작업(무정지 설비), 작업 시간대 조율, 방화벽·망 변경 |

- **자산이 먼저 알려 준다.** 시험 자산에는 `patchConstraints`(예: `vendor_approval`, `no_downtime`, `maintenance_window`)가 있다. `vendor_approval`이 있는 자산은 협력사 승인, `no_downtime`·`maintenance_window`가 있는 자산은 타 팀 승인이 필요하다고 요청 화면에 미리 표시한다.
- **요청에 기록한다(제안, 첫 버전의 최소형).** 요청 작성 시 "외부 승인 필요" 항목마다 승인 대상(협력사 또는 팀 이름), 승인 상태(요청 전·요청함·승인·거절), 승인 일시, 증빙 메모(회신 메일 요지, 문서 번호 등)를 입력한다. 외부 담당자는 계정이 없으므로 **신청자가 대신 기록**한다.
- **신청자의 기록은 증빙의 요약일 뿐이다.** 신청자가 직접 입력하므로 위조·자기 확인을 막을 수 없다. 그래서 admin이 승인할 때 필요한 외부 승인 항목의 상태가 "승인"이고 증빙 메모가 있는지 직접 확인해야 하며, 확인하지 않으면 승인할 수 없다. 외부 승인이 하나라도 빠졌거나 거절이면 내부 승인(`approved`)을 막는다. 이는 서버가 검사한다.
- **외부 승인은 내부 승인을 대신하지 못한다.** 협력사나 타 팀이 승인해도 admin 승인은 따로 필요하다. 반대로 admin 승인만으로 외부 승인을 건너뛸 수 없다.
- **인수 기준(제안):** 외부 승인 필요 표시가 있는 요청에서 (가) 항목이 하나라도 "승인"이 아니면 admin 승인 시도는 거부된다. (나) 모든 항목이 "승인"이고 증빙이 있으면 승인 가능하다. (다) 외부 승인 항목을 수정하면 변경 이력이 남는다.
- **후속:** 내부 타 팀 담당자가 앱에 직접 들어와 읽기·의견·승인만 하는 확인자 역할. 협력사 계정은 외부 접근 범위 설계가 따로 필요해 범위 밖으로 둔다.
- **결정할 것(확인 필요):** 협력사 승인을 앱에 직접 받을지(계정) 신청자가 증빙으로 기록할지, 내부 타 팀 승인을 어느 팀까지 요구할지, 승인 요구를 자산의 `patchConstraints`에서 자동으로 정할지 사람이 정할지.
- 역할과 화면이 늘면 DB 접근 규칙, 권한 시험, 화면이 같이 늘어난다. 현재 DB 규칙에 결함이 있어(7절) 먼저 고쳐야 한다. 이 제안의 공수는 팀 추정에 들어 있지 않다.

### 10-2. 새 보안 공지가 들어왔을 때의 장비 추적 (제안, 팀 미채택)

별도의 "제품 목록" 개념은 두지 않는다. 장비(자산) 한 건에 **어떤 제품이 들어갔고 펌웨어·버전이 무엇인지**만 적어 둔다. 수집기가 계속 공지를 모으다가 긴급 보안 패치 내용이 들어오면, 그 제품이 들어간 장비를 찾아 내용을 공유하고 경고할 점이 있는지 확인한다. 판정은 공지가 들어온 시점에 계산하며 장비 데이터에 미리 저장하지 않는다. 팀이 채택하기 전까지는 요구가 아니다.

**흐름**
1. 수집기가 소스를 주기적으로 수집한다. 첫 버전은 CISA KEV이며, 새로 등록된 항목(`dateAdded`)이 "새 공지"다.
2. 새 공지의 제조사·제품 문자열로 장비를 찾는다(후보, `candidate`). FR-07과 같다.
3. 후보 장비의 버전을 공지의 영향 범위와 사람이 확인한다(AP 절차). 버전이 비어 있으면 "미상"이라 "확인 필요"로 남긴다.
4. 확인한 결과를 담당자·관리자에게 공유하고, 패치 요청이 필요하면 요청 흐름(FR-11~14)으로 넘긴다.

**장비가 가지는 정보:** 제조사, 제품(모델), 펌웨어·소프트웨어 버전, 도입 연도(알면). 버전은 자산 입력(FR-03)의 기존 필드이므로 새 요구는 펌웨어 표기와 도입 연도 칸 정도다. EPSS·CVSS·판정 결과는 장비 데이터에 넣지 않는다.

**첫 버전(3일)에서 하는 것:** 위 흐름 1~4. 제조사 공지는 **공지 링크와 영향 범위 원문을 사람이 붙여 넣는 칸**으로만 받는다.

**후속으로 두는 것:** 제품·버전을 영향 범위와 **자동 비교**해 영향 여부를 표시하는 기능, 제조사 공지의 자동 수집. 공지가 자유 문서·PDF·로그인 필요 자료인 경우가 많아 3일 안에 파싱할 수 없고, 이미 제외한 NVD 영향 버전 매칭과 같은 성격이다.

| 소스 | 지금 PRD | 제안 |
|---|---|---|
| CISA KEV | 필수(FR-05·06·07) | 그대로. "실제 악용 사례 있음" 표시의 근거. KEV에 없는 취약점은 "악용됨"으로 표시하지 않는다 |
| EPSS | 선택(FR-24, Could) | 첫 버전에 넣지 않는다. 쓰게 되면 수집기가 공지 시점에 가져오는 참고값이고, 값이 없으면 0점으로 대신하지 않는다 |
| 제조사 보안 공지 | 소스로 없음 | 첫 버전은 수동 붙여넣기. 자동 수집은 후속이며 수집 방식·이용 조건은 **확인 필요** |
| NVD 영향 버전 | 첫 버전 제외 | 계속 제외 |

**시험용 데이터셋과의 관계:** `dataset-v2`의 자산 데이터는 제품·버전·위치만 담고 공지가 없다. 수집기 결과를 비교하는 QA용 정답지(`*_expected_matches.json`)는 자산 목록과 별개의 시험 자료이며 앱이 읽지 않는다. 정답지의 EPSS는 시뮬레이션 값이다. 정답지를 저장소에 둘지는 팀이 정한다.

**자산 목록에는 공지를 넣지 않는다.** 자산 한 건은 제품, 펌웨어·버전, 위치(공장·라인·구역·망), 담당자 같은 정보만 가진다. 공지와 CVE는 수집기가 가져오는 외부 정보이고, 장비와의 연결은 공지가 들어온 시점의 **매칭 결과**로만 생긴다. 그래서 "가상 제품에 실제 CVE를 붙이지 않는다"는 팀 규칙과 부딪히지 않는다. 자산 데이터에는 실제 CVE가 하나도 없다. 매칭 결과를 화면에 보일 때는 가상 자산 기준의 시험 결과임을 표시한다.

- 새 소스는 수집 방식, 저장 표(DB 변경), 갱신 실패 처리, 출처 표시가 추가로 필요하다. 공수 추정에 들어 있지 않다.
- 팀 지침(NVD 제외, EPSS는 여유 시)과 맞는 방향이다. 제조사 공지 소스를 넣는 것만 팀 합의가 필요하다. **확인 필요.**
- 정답지에 가상 자산 ID와 실제 CVE가 함께 있는 점이 걸리면 정답지는 저장소에 올리지 않고 로컬 시험에만 쓴다.
